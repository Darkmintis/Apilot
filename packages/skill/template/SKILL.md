# Apilot — AI Workflow Guide

> This file lives at `.apilot/SKILL.md` inside your project. It is the
> instruction set for any AI assistant working on this codebase. Apilot
> generates it automatically from the extension's "Connect AI" command and
> updates it whenever your API definitions change.

## 1. What is Apilot?

**Apilot** is a VS Code extension that makes API integration boring and
error-free. It lives inside your editor, stores everything as plain text
files under `.apilot/`, and gives you a **real-response-first** workflow:

1. Endpoints are defined once as YAML files (not Postman collections).
2. You run them for real — the actual request and response are captured.
3. Snapshots (saved responses) become the source of truth for codegen,
   schema inference, and drift detection.
4. When the backend changes, Apilot diffs the new response against the
   snapshot and tells you exactly what broke.
5. You generate typed models and API calls — the AI never guesses field
   names or response shapes.

**One-line pitch:** Postman + response diff + AI-native codegen, living in
your codebase.

## 3. How the AI should work with Apilot

### The core rule: **never guess, always run first**

Before writing or modifying any API code, follow this sequence:

1. **List endpoints** — call `list_endpoints` to see what's available.
2. **Run the endpoint** — call `run_endpoint` with the right environment to
   see the real response. The AI needs the actual data, not a guess.
3. **Get the schema** — call `get_schema` for typed field info (nullable,
   type, enum values).
4. **Generate code** — call `generate_code` for the target language.
   Use its output verbatim.
5. **Never edit generated files** — generated code has a header. Hand-write
   in separate files only.

### When the backend changes (drift flow)

1. Call `diff_endpoint` to compare the latest snapshot against the baseline.
2. If there are breaking changes, call `impact_report` to see which files
   and models are affected.
3. Fix only what's affected — do not touch unrelated code.
4. Run `run_endpoint` again to confirm the fix works.

### Bug investigation flow

1. User says: "Login fails in the app."
2. Call `run_endpoint` for the login endpoint.
3. Compare the response against the snapshot using `diff_endpoint`.
4. If the response differs, read the diff and the impact report.
5. The fix is usually in the client code that consumes the changed fields.

## 5. Critical rules

### 5.1 Secrets
- **Secret values never appear in any file** in the repo or in AI context.
- The `authToken` variable is typed as `type: secret` in the environment
  file. Its actual value lives in the VS Code OS keychain.
- `list_variables` returns names and types only. Do **not** ask for,
  request, or attempt to log secret values.
- Snapshots are automatically redacted. Masked values appear as `⟦REDACTED⟧`.

### 5.2 Generated code
- Generated files have a header: `// Generated by Apilot. Do not edit.`
- Custom code should live in **separate** files (e.g., `user_api.custom.dart`).
- If you need to change a generated model, change the schema in
  `.apilot/schemas/` and regenerate.
- Codegen is **diff-aware**: only models whose schema changed are updated.

### 5.3 Drift detection
- The diff engine classifies changes as: **breaking**, **warning**,
  **non-breaking**, or **info**.
- Breaking changes fail builds in CI (`apilot check`).
- `nonNullableToNullable` (field became nullable) is **non-breaking**.
- `nullableToNonNullable` (field became required) is **breaking**.
- Field type change is always **breaking**.
- A new enum value is a **warning** (unhandled in client).
- An enum value removal is **breaking**.
- A field with the same type and position but a different name is
  flagged as **"likely rename"** — verify before treating as breaking.

### 5.4 File format
Endpoints are YAML. Variables use `{{varName}}` syntax. Example:

```yaml
name: List orders
method: GET
url: "{{baseUrl}}/orders"
auth: { type: bearer, token: "{{authToken}}" }
query: { page: "1", limit: "20" }
headers: { Accept: application/json }
body: null
expect:
  status: 200
  schema: ../../schemas/orders.list.json
after:
  - set: { orderId: "$.data[0].id" }   # chain into next request
```

### 5.5 Environments
- `dev.yaml`, `prod.yaml`, etc. live in `.apilot/environments/`.
- Text variables have `type: text, value: "..."`.
- Secret variables have `type: secret` — the value is in the OS keychain.
- On a fresh clone, Apilot prompts: "Enter values for: authToken, ..."
- Missing secrets on a fresh clone trigger a prompt.

## 7. Quick reference for common tasks

### Add a new endpoint
1. `add_endpoint` with method, URL, and a cURL or OpenAPI snippet, OR
2. Create `.apilot/collections/users/list.yaml` manually and call
   `list_endpoints` to verify it was picked up.

### Run an endpoint
1. `run_endpoint endpoint-id="orders.list" env="dev"`
2. Read the redacted response in the result.

### Detect backend drift
1. `run_endpoint endpoint-id="orders.list" env="dev"`
2. `diff_endpoint endpoint-id="orders.list"`
3. If breaking: `impact_report endpoint-id="orders.list"`

### Generate code
1. `generate_code endpoint-id="orders.list" language="dart"`
2. Review the generated file at the output path.
3. Do NOT edit the generated file. Add custom code in a separate file.

### Import existing Postman collection
1. `import_spec source="postman" path="/path/to/collection.json"`
2. Apilot creates `.apilot/collections/` entries automatically.

## 8. Fallback: reading files directly

If the MCP server is unavailable (e.g., the editor is not open, or you're
in a plain text environment), you can read these files directly:

- `.apilot/apilot.yaml` — project config
- `.apilot/environments/dev.yaml` — environment variables
- `.apilot/collections/**/*.yaml` — endpoint definitions
- `.apilot/snapshots/**/*.json` — saved responses (already redacted)
- `.apilot/schemas/**/*.json` — inferred schemas

**Remember:** snapshots and schemas are safe to read. Secret values
are **never** written to any file in `.apilot/`.
